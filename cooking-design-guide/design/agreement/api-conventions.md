# api-conventions.md — 接口设计约定

> 本项目接口层的**统一协议约定**。所有后台接口服务（后端接口服务对外提供的 API）的返回格式必须遵循本约定。
> 本文件为稳定约定，修改须经用户明确确认。

## 适用范围

- 后端接口服务对外提供的所有 API（前端调用、Agent 反向调用）。
- 采用 **JSON 信封结构** + **REST 风格**，状态码对齐 HTTP 语义。

## 统一返回格式

所有后台接口服务的返回均为 JSON 信封结构：

```json
{
  "code": 200,
  "data": {},
  "message": "ok"
}
```

| 字段        | 说明                                                                          |
| ----------- | ----------------------------------------------------------------------------- |
| `code`    | 状态码（数值），与 HTTP 响应状态码一致（见「状态码约定」）                    |
| `data`    | 实际返回数据层。结构随接口需求而定，可为任意类型（对象 / 数组 / 标量 / null） |
| `message` | 状态解释。成功为 `ok`；失败/异常时为可读错误描述文本                        |

> 各业务接口在 `data` 内的具体结构见对应迭代设计文档（`design/sprints/<Sx>/api.md`）。

## 状态码约定

`code` 与 HTTP 状态码**保持一致**：HTTP 响应状态码即 `body.code`，客户端任选其一判断，二者无差异。

| code | 语义                                           | `data` | `message`        | 典型场景                                              |
| ---- | ---------------------------------------------- | -------- | ------------------ | ----------------------------------------------------- |
| 200  | 成功                                           | 实际数据 | `ok`             | 正常返回                                              |
| 400  | 请求格式错误（缺少必填、类型错误、枚举非法等） | `null` | 具体错误描述       | 请求体/路径/查询参数不合法                            |
| 404  | 资源不存在                                     | `null` | 具体资源不存在描述 | 菜谱 id 不存在、成员不存在                            |
| 409  | 资源冲突 / 状态不允许                          | `null` | 具体冲突描述       | 删除被引用资源、重复创建                              |
| 422  | 请求体语义/业务校验失败                        | `null` | 具体描述           | 参数校验失败（FastAPI/Pydantic 默认）、业务规则不满足 |
| 500  | 服务器内部错误                                 | `null` | 兜底文案           | 未捕获异常、数据库错误                                |
| 502  | 上游（Agent）不可用                            | `null` | 降级文案           | Agent 服务宕机                                        |
| 504  | 上游（Agent）超时                              | `null` | 降级文案           | Agent 决策超时                                        |

### 约定细则

1. **无结果（候选耗尽 / 无合适菜谱）**：视为**正常业务结果**，返回 `code=200`，`data` 为空集合，`message` 给出业务提示（如 `"没有合适的菜了"`）。前端以 `data` 是否为空判断并展示提示。与当前 S1 决策接口处理一致。
2. **参数校验失败统一用 `422`**：跟随 FastAPI/Pydantic 默认行为，前后端统一按 `422` 处理参数/请求体校验错误；`message` 给出可读的错误描述。
3. **错误时 `data` 默认 `null`**：除非某接口约定返回字段级错误明细（此时 `data` 为对象结构，具体见迭代文档）。
4. **`message` 仅作展示**：前端业务分支一律以 `code` 判断，不解析 `message` 内容。成功固定为 `ok`，错误用可读文本（中文）。
5. **未定义的异常**：兜底为 `500`，`message` 使用通用文案，不向客户端泄露内部细节（栈信息等）。

## 接口命名与结构约定

### 路径

- 统一前缀 `/api`（当前后端 `FastAPI` 已在 `/api` 挂载路由）。
- 资源使用**复数名词**，小写、`_`（下划线）分隔，如 `/api/members`、`/api/recipes`。
- **路径不拼接资源 id**：资源 id 一律以参数传输（`body` 或 `query`），便于未来扩展批量操作。
  - 单资源更新 / 删除：`PUT` / `DELETE` 在请求体携带 `id`
  - 单资源查询（若未来需要）：`GET` 用查询参数 `id`
  - 批量操作：预留请求体 `ids` 数组
- 子资源路径（若有）用 `/{resource}/{sub}`，id 仍走参数。
- 不引入 `/v1` 版本前缀；若未来需版本化，再统一加前缀。

### 动词与语义

| 方法   | 语义            | 说明                                 |
| ------ | --------------- | ------------------------------------ |
| GET    | 查询 / 读取     | 只读，幂等，无副作用                 |
| POST   | 创建 / 触发动作 | 非幂等；可用于无实体资源的动作型接口 |
| PUT    | 全量更新        | 幂等                                 |
| PATCH  | 部分更新        | 部分更新字段                         |
| DELETE | 删除            | 幂等                                 |

> 动作型接口（如决策）用 `POST` 表达"触发一次操作"，路径用动作名词，如 `/api/decisions`。

### 字段命名

- 请求/响应字段统一 **snake_case**（与后端 Python 惯例一致）。
- 布尔字段用 `is_` / `has_` 前缀（如 `is_active`），或语义化命名。

### 时间与 ID

- **时间**：统一 **ISO 8601** 字符串（如 `2026-08-22T13:00:00+08:00`），UTC 存储、本地展示由前端处理。
- **ID**：数值自增（与数据层 `t_*` 表主键一致）；路径/查询参数中的 id 为整数。

## 分页约定

列表类接口统一支持分页（如有需要），约定如下：

**请求参数**（query，`GET`）：

| 参数          | 类型 | 默认   | 说明                   |
| ------------- | ---- | ------ | ---------------------- |
| `page`      | int  | `1`  | 页码，从 1 开始        |
| `page_size` | int  | `20` | 每页条数，上限 `100` |

**返回结构**（`data` 内层）：

```json
{
  "list": [],
  "has_next": true,
  "total": 0,
  "page": 1,
  "page_size": 20
}
```

| 字段          | 说明                                                 |
| ------------- | ---------------------------------------------------- |
| `list`      | 当前页数据数组                                       |
| `has_next`  | 是否还有下一页（布尔），供前端提前判断是否可继续翻页 |
| `total`     | 总条数                                               |
| `page`      | 当前页码                                             |
| `page_size` | 当前每页条数                                         |

> 当前 S1 决策接口/菜谱查询是否分页，见对应迭代文档；本约定为列表接口的通用规范。列表接口**统一返回 `total` 与 `has_next`**。

### `has_next` 实现方式

`has_next` 在服务端可直接实现，且**无需额外统计 `total`**：

- 查询时取 `page_size + 1` 条（`LIMIT page_size OFFSET (page-1)*page_size`，实际取 `page_size+1` 条）。
- 若实际取到 `page_size + 1` 条 → 存在下一页，`has_next = true`；否则 `has_next = false`，并丢弃多取的那 1 条。
- 该方式只多查一条记录，代价极低；`total` 仍独立统计（`COUNT(*)`），供前端展示总条数。

## 幂等与请求 ID

- **只读接口（GET）**：天然幂等。
- **同步动作接口**：本项目为单用户本地应用，同步交互，**不引入幂等键**；重复提交由前端交互控制（如禁用按钮）。
- **请求 ID / 追踪**：暂不引入 `request_id` 作为协议字段；如需排查可依赖服务端日志。

## 鉴权与 CORS

- 本系统为**单用户本地应用，无账号体系**（见 `service-overview.md`），接口**不要求鉴权**。
- 前后端同机部署（docker-compose），CORS 按部署需要配置；不引入 token / 会话机制。

## 健康检查

- 健康检查接口（`/api/health`）用于服务存活探测，**不套业务信封**，返回精简结构（如 `{"status":"ok"}`）。
- 业务接口一律遵循统一信封；健康检查为运维专用例外。

## 与 HTTP 状态码对照

由于 `code` 与 HTTP 状态码一致，以下是对照速查：

| HTTP 状态码           | body.code | 前端处理建议                        |
| --------------------- | --------- | ----------------------------------- |
| 200                   | 200       | 解析 `data` 渲染                  |
| 400 / 404 / 409 / 422 | 同值      | 展示 `message` 提示               |
| 500                   | 500       | 展示通用兜底提示                    |
| 502 / 504             | 同值      | 展示"服务/Agent 暂时不可用"降级提示 |
