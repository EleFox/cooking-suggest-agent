# integrations.md — 集成设计

> 描述与本系统对接的外部服务设计。本系统唯一外部服务为 **Agent 决策服务**。

## 外部服务

| 服务 | 说明 |
|---|---|
| Agent 决策服务 | 决策核心（知识库查询、推荐方向、候选筛选确认、最终排序），由用户自建，与前后端同机部署（docker-compose），内部实现不在本设计范围 |

## 内部服务

- 前端应用（容器）
- 后端接口服务（容器）
- 两者通过 HTTP 交互，前端调用后端接口服务

## RPC / API

### 对外 API（本系统 → Agent）

**决策请求**（前端 → 后端接口服务 → Agent 透传，同步）

- 入口：前端调用后端决策接口
- 后端组装决策上下文后透传给 Agent（HTTP POST）
- 决策上下文包含：
  - 启用的成员及偏好/禁忌要素（前端展开为 `elements`；服务端透传前 enrich 为 `{id, type, name, sort_order, relation_type}`）
  - 料理偏好要素（手段/时间）
  - 决策因素权重（首次传入，Agent 判断）
  - 自由文本需求（US-05，若后续启用）
  - 去重列表：前端传入已生成菜谱 id 数组，服务端透传前翻译为完整菜谱 `{id, name, elements, detail}`（含做法正文）
  - 生成数量 n
- 调用模式：**方案 C 同步 + 超时兜底**；Agent 端自限时限；Agent 可能返回"无结果"

### 反向 API（Agent → 本系统）

**菜谱查询 API**

- 用途：Agent 按推荐方向筛选候选菜谱
- 方法：GET `/api/recipes`
- 入参：关键字查询（菜名）、去重参数 `exclude_recipe_ids`（逗号拼接的已生成/已选菜谱 id，返回结果中排除）、分页参数（分页参数与返回结构遵循 `design/agreement/api-conventions.md` 的分页约定，含 `has_next` / `total`）
- 出参：**菜谱摘要列表**，每项 `{id, name, elements, has_detail}`——`elements` 为该菜谱全部关联要素数组 `[{id, type, name, sort_order}]`，不含做法全文；按统一信封 `data.list` 返回，附 `has_next` / `total` / `page` / `page_size`
- 硬过滤（禁忌要素）**由 Agent 端在获取候选后自行处理**；去重通过 `exclude_recipe_ids` 入参支持
- 排序相关度：**搁置**，暂不提供显式相关度排序

**菜谱详情 API**

- 用途：Agent 筛选后最终确认；详情页前端复用（菜谱编辑回显）
- 方法：GET `/api/recipes/detail`
- 入参：菜谱 id，支持逗号拼接批量传入（`ids=1,2,3`，不设数量上限）
- 出参：**不分页 JSON 数组**，每项 `{id, name, elements, detail}`——`detail` 为做法正文文本（无详情为 `null`）；不存在的 id 忽略

### 决策结果返回（Agent → 后端接口服务）

- 选中的菜谱 id 列表（+ 可选理由）
- 后端据此组装卡片 JSON（elements 数组）返回前端
- 可能返回"无结果"（Agent 判定无合适菜谱）

## 消息队列

无。全部为同步 HTTP 调用，不引入消息队列。

## 事件

无事件机制。决策过程由 Agent 端内部循环驱动，本系统不感知中间状态。

## 调用方向

```
前端 ──决策请求──▶ 后端接口服务 ──透传──▶ Agent 决策服务
                        ▲                     │
                        │                     │ 反向调用
                        │                     ▼
                        │            【菜谱查询 API / 详情 API】
                        │                     │
                        └──结果(同步)◀────────┘
后端接口服务 ──结果卡片 JSON──▶ 前端
```

## 数据交换

| 交换 | 方向 | 格式 |
|---|---|---|
| 决策上下文 | 后端→Agent | JSON（富化 elements + 完整 dedup 菜谱 + 权重/数量） |
| 菜谱摘要列表 | Agent←后端 | JSON（id/name/elements 数组/has_detail） |
| 菜谱详情 | Agent←后端 | JSON（id/name/elements/detail 文本，批量数组） |
| 决策结果 | Agent→后端 | JSON（选中菜谱 id 列表 + 可选理由） |

## 超时

- 决策请求（后端→Agent）：设置超时上限；Agent 端自限时限，**超时兜底由前端显示**
- Agent 反向调用查询/详情 API：由 Agent 端控制循环节奏，本系统按常规接口超时处理

## 重试

- 本系统对 Agent 决策请求**不做重试**（同步长耗时，重复提交由用户操作触发）
- Agent 对查询/详情 API 的重试由其内部循环逻辑控制，本系统不干预

## 幂等

- 菜谱查询/详情 API 为**只读**，天然幂等
- 决策请求透传为纯转发，不产生服务端持久化副作用（使用记录 P2 独立处理）

## 失败处理

| 场景 | 处理 |
|---|---|
| Agent 超时/不可用 | 后端返回错误，前端兜底显示（提示稍后重试） |
| Agent 返回"无结果" | 后端原样返回，前端兜底显示"无合适菜谱"提示 |
| Agent 降级 | 无显式降级链（决策核心在 Agent，本系统不做规则降级排序）；具体降级策略由 Agent 端负责 |

## 依赖约束

1. Agent 服务与前后端容器**同机部署**（docker-compose 编排），反向 API 走本机网络，无跨机鉴权需求
2. Agent 服务的接口契约由 Agent 端维护；本系统仅按既定协议透传与接收
3. 菜谱查询/详情 API 同时服务前端详情页，是稳定接口，需与 Agent 端协商冻结后再实施
4. 排序相关度设计搁置，后续如需调整接口契约须在本文件更新并经用户确认
